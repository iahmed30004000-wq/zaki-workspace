# C3b.6 — «@» walks the unread mentions, and the check of «مين شاف»

## Definition of Done
- What must work: (1) **The door.** `GET /api/chat/conversations/[id]/mentions?after=&limit=` answers `{ ids, next }`: the ids of the UNREAD messages of the conversation that mention me (by id) or everybody («@الكل»), oldest to newest, `limit` 1..100 (50 by default), `next` = the last id when there are more (pass it as `after`; the cursor is the message's `(createdAt, id)`, so two messages of the same instant are neither skipped nor repeated). `withApi` + zod (`mentionsQuerySchema`; a bad `limit` is the usual 422). (2) **The reading rule** is the one of opening the conversation: `canRead` first (404 for a restricted topic that is not mine, somebody else's chat, another company, a conversation that is not there; a guest has topics only). (3) **The same «unread» as the chat list** (C1.2's rule, copied from `queryConversations`): after MY read mark, never my own message, never a deleted one, never a system line, never an archived conversation, and only with a read mark of my own (no row = nothing counted) — so the list's `mentionsUnread` and the length of this list are the same number, and nothing about that number changed: the door is read-only. (4) **Privacy.** A reader in silent oversight (no row of his own) gets an EMPTY list and the door writes nothing: no `ConversationMember` row, no realtime event, no read mark. A deleted message never appears. The answer is ids and a cursor: no text, no author. (5) **The walk.** The «@» button no longer sees only the newest N LOADED mentions: `useMentionsWalk` (in `floating.tsx`) asks the door when the row says there are unread mentions (and again when that number moves), and each press goes to the next one NOT yet visited, oldest to newest, through `jumpTo(id)` (which loads the window around a message that is not loaded). While the list is not here (not asked yet, the request failed, or it is empty while the row still counts some) the loaded mentions are the walk, as before. Visited ids that the server no longer lists as unread are dropped (`pruneVisited`). (6) **«مين شاف»** — checked, nothing added (below).
- Tests: `tests/db/chat-mentions-route.test.ts` (10: the list oldest first with `@الكل`, never mine / deleted / system / read / somebody else's; the list's number and this list agree and asking changes neither; pages with a cursor and a tie in time; bad paging; no read mark = empty and no row made; archived = empty; a private chat; the refusals; silent oversight = empty, no row, no event; asking twice leaves the mark), `tests/db/privacy-matrix.test.ts` (+4: the C3b.6 row for open / restricted / team / DM over all nine personas: who may ask, who gets ids, nobody leaves a row or an event, no answer carries a text), `tests/chat-v2-pane-model.test.ts` (+7: `walkTargetsOf`, `pruneVisited`, the walk oldest to newest, `unreadMentionsUrl`, `collectUnreadMentions` with its page cap and its all-or-nothing failure rule).
- Edge cases that matter: two mentions in the same instant; a mention whose message is far above the loaded window; the server list empty while the row still counts (a race: the loaded ones stay the walk); a mention read since (it leaves the visited ids); the cursor of another conversation or of nothing is «not found», not a start from the top; the owner who joined the conversation has a row and so has his OWN list, like the chat list's number for him.
- Blockers: CI red · an old test red · a secret exposed · a destructive migration (none: no schema, no migration, no new switch, no dependency).

## «مين شاف» — verified, nothing duplicated
Built in C2.6 (`pr/C2.6+C2.7.md`): the registry item `seen` («مين شاف», `surface: "v2"`, a topic or a group, offered only when somebody's NEWEST read message is this one — `readerCount > 0`) opens `SeenDialog` (a small dialog with today's `ReaderList`, and the line «ما حدا قرأها بعد» when nobody did) in `pane/seams/menu-host.tsx`. The readers come from the messages window (`readersOf`): the person themselves and the silent owner (`silentOwnerIds`) are not in the list, a deleted message is skipped (its readers sit on the previous visible message), and a private chat has none (ticks instead). The spec's behaviour is all there, so no code was added; the existing tests (`chat-v2-menu-registry`, `chat-v2-menu-render`) pin it.

## Independent review
There is no tool in this worker session to start a separate agent, so the review was the `code-review` skill (a forked, read-only reviewer that reads the diff and runs nothing). Its first run read another checkout (a different branch); the second, pointed at this worktree's staged diff, gave 8 findings. Each was judged here.
- **Real, fixed (the first with its test written and seen red first):** (1) a list cut short by a failed page 2+ passed for the whole list, so the walk stopped at the first page while the badge still counted more — `collectUnreadMentions` now throws on ANY failed page and the loaded mentions stay the fallback (test: «ANY failed page throws»); (2) the «ask now, then jump» fallback of the hook could jump in the NEXT conversation when the person switched meanwhile — it checks the live conversation after the answer; (3) `visited` was reset by an effect, so for one render after a switch it held the previous conversation's ids — it is kept with its conversation id, like the list; (4) the door ran one query more than needed (the read mark and the archived flag are ONE query now); (5) `out.includes` / `listed.includes` were quadratic — a `Set`.
- **Real, fixed in the docs:** C3b.6 was ticked done while the viewport does not call the hook yet — README and the spec now leave it unticked (the progress row says «built»), with the exact wiring written under «Not done here».
- **Answered without a change:** the refetch when the unread number moves is kept: it is one page for nearly everybody (50 mentions), a jump does not mark anything read (only reaching the bottom does, usually to 0, which asks nothing), and the list must drop what was read; a deleted-then-PURGED cursor message makes the door answer «not found» like the messages door does (a soft delete still resolves) — the client then falls back to the loaded mentions (finding 1), and a purge in the middle of a walk is rare.
