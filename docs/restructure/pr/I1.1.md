## Why `IdempotencyRecord` cannot hold the deliveries
Its `tokenId` is required and points at an API token (`ApiToken`), and a signed delivery from the orders system has no token: it is proved by the HMAC of a secret that belongs to the receiver. Its key is also built from a
token and a request kind. A new table with the three-column unique index is the whole guard. It holds NO body: company, source, the sender's delivery id, the event name (kept for the daily counts) and the time.
The same table serves the daily card's «once a day» claim (source `oms-daily`, the day as the id).

## Choices worth a look
- **A row of its own for the receiver** (`IntegrationType.OMS_EVENTS`) instead of keys inside the `OMS` row of Q1.0: the Q1.0 save overwrites `secretEnc` with `{ token }` and the removal deletes the row, so a receiver kept there would lose its
  secret when the owner re-saved the token. The secret is still encrypted in `Integration.secretEnc`, beside the token's row.
- **v2 has its own gate** (`authenticateMessages`) instead of calling v1's `authenticateDoor`: v1's gate counts against v1's limit of 60 a minute and checks only `apiDoor`; the contract asks for 120 a minute and its own switch. The order of the checks and the
  answers are v1's. `api-door.ts` is untouched and every v1 test is green.
- **The door's card is not `sendMessage`**: that path counts the author's 30 sends a minute (the token's person would be limited as a human and a human by the token), accepts only the two cards of the composer and refuses «لازم ينقرأ» on a card.
  `storeAppCard` writes the same rows (message, last-message time, live event) in the caller's transaction.
- **Until the chat screen draws this card, it shows as text**: the redaction layer (`redact.ts` / `dto.ts`) knows only the product and order cards, so the message's `body` carries the whole card as plain words (the key's name first, the title, the lines, the order number, each button's label and address).
- **The ticket rule by event is stored in `autoTicketRules`** as `type: "event"` entries. `src/lib/tickets/auto-rules.ts` (not a file of this package) does not know the kind and skips it, so message-time rules never see it; `problem-settings.ts` reads and writes it and keeps it when the other rules are saved.
- A button's address is guarded too: a run of seven digits or more in it is refused (the contract says so and tells the sender to use `ref`).

(e) efficiency: the daily job does three queries per company on every 30-second tick after the card was sent, `saveEventsSettings` checks its topics one after the other, and the day-claim rows of source `oms-daily` are never pruned; (f) `scheduler.ts` runs the daily card inside the same `Promise.race` as the due jobs, so a timeout leaves the daily work running while the next tick starts (the day claim prevents a second card).

## Self-review (what it found, all fixed with a test)
1. The daily job gave the day back on every failure, so a topic archived for good would have written a failure row every 30 seconds: a failure that will not mend keeps the day taken (one row); one that may mend gives it back, and its row is written at most once in ten minutes.
2. Nothing slowed a guess at the receiver's secret: an address with 30 refused deliveries in 10 minutes is answered 429 (a good sender is not counted).
3. The delivery rows would grow for ever without a daily card: old rows are removed now and then (a hundredth of the deliveries) and when the card is sent.
4. A delivery whose header names another event than its body is refused; a body whose order number has not the orders system's shape writes no state (it is still counted).
