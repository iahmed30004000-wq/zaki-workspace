# C1.8 — Sending, receipts, typing

## Definition of Done
- What must work: (1) **The first attempt is optimistic.** The composer (new screens only: it needs the optional `optimistic` prop, the chat cache's QueryClient, AND an outbox) writes a pending copy of a plain text into the newest window of the cache the moment send is pressed (`src/lib/chat/cache/pending.ts`: `appendPending`, `replacePending`, `failPending`, plus `resumePending`, `removePending`, `dropStalePending`, `syncPendingWithOutbox`), the box is free at once, and the server's answer — or the sync, whichever comes first — replaces it IN PLACE, found by the `clientId` of my own message: never a duplicate. A failure is handed to the existing outbox with the SAME `clientId`: no network or 502/503/504 → kept for its retry (the clock stays); 429 → kept with its Retry-After; a refusal → kept MARKED (`Outbox.enqueue(..., { failed })`, new option) and the bubble turns red with a «!» and the reason, with «إعادة المحاولة». (2) **The send answers right after the commit.** The bell, the push and the company's auto-ticket rules run after the answer (`runAfterSend` in `messages.ts`); a step that throws is logged with `log.error("chat.after_send_failed", { step, name })` (never the text) and never fails the send; the audience and the F0.5 push rule are untouched. (3) **Read marks are deltas.** `createReadMarker` (`src/lib/chat/read-gate.ts`): a mark goes out only when the tab is visible AND focused and only when the newest read message CHANGED; never for the owner's silent oversight, a pending message, or older messages shown around a search hit; a delivered mark is written only when the other person wrote something newer; the other clients apply the `reads` list of the sync answer (C1.4's `applyReads`), no refetch. (4) **Typing is cheap.** `src/server/chat/typing-gate.ts`: the policy facts of (person, conversation) are remembered for 30 s in the typing route (a ping used to cost about 12 calls).
- The writers C1.1 left behind: `forwardMessage` and `writeSystemMessage` (every system line: join, leave, pin, close, a call, a rule) now move `Conversation.lastMessageAt` with the same guarded update, in their own transaction (one shared function, `moveLastMessageAt` in `system.ts`, also used by the send).
- Tests: `tests/db/chat-send-after-response.test.ts` (5), `tests/db/chat-typing-gate.test.ts` (10), `tests/db/chat-send-reads.test.ts` (7), `tests/db/chat-last-message-at.test.ts` (+4: forward, a pin's system line, never backwards), `tests/db/privacy-matrix.test.ts` (+4 rows: who may mark read, who leaves a trace, who may mark delivered, per kind and persona), `tests/chat-optimistic-pending.test.ts` (22), `tests/chat-optimistic-send.test.ts` (11), `tests/chat-optimistic-read-gate.test.ts` (15), `tests/chat-optimistic-composer.test.ts` (7), `tests/chat-outbox-queue.test.ts` (+3), `tests/chat-outbox-ui.test.ts` (+3).
- Edge cases that matter: the answer and the sync both bringing the same message in either order (one copy); two messages in flight settled by their own `clientId` in any order; somebody else's message that carries my `clientId` replaces nothing; a pending bubble never sorts above a message that was already on screen (a clock behind the server's); a refusal is never retried by itself and survives a reload; a retry can never send twice (`clientId`, F0.7: the idempotency check still runs BEFORE the rate limit; `chat-send-idempotent-limit` and `chat-outbox-idempotency` stay green); the typing memory never stores a refusal, is keyed by person AND conversation AND company, is never used for the owner, and a person removed from the audience loses typing within 30 s; the owner's oversight leaves no read mark, no event and no notification.
- Blockers: CI red · an old test red · a secret exposed · a destructive migration (none: no schema change, no migration, no new dependency, no feature switch).

- **`src/lib/chat/cache/pending.ts`** (new, one export block appended to `index.ts`; the writer is not edited: pending uses its `replaceMessage` and `upsertRows`, and the reducers' `mergeMessage`), **`src/lib/chat/outbox/optimistic.ts`** (new: `startOptimisticSend`, `retryPending`, `discardPending`), **`queue.ts`** (`enqueue` option `failed`), **`read-gate.ts`** (`createReadMarker`), **`chat-composer.tsx`** (additive: the `optimistic` prop, one branch in `submit`, one effect), **`pending-bubble.tsx`** (the red «!»; the bubble also draws a cache pending message through `outboxItemOfPending`).

**Time from send to ✓, measured by a DB-level test of the route's own awaited work** (`chat-send-after-response`, a DM with one recipient, 7 sends each, a shared machine with other workers running, the call helper's own overhead included): **before** (the notification inside the call) median 143 ms (min 103, max 242); **after** (answer right after the commit) median 88 ms (min 80, max 104). A browser's real ✓ adds the network and the render and is not measured here (see Owner actions). With a recipient that has several devices, or a topic with many mentions, the saving is larger: the notification work grew with the audience, the answer no longer does.
