# C3b.5 — «حدّد»: select many messages, forward them, delete them, make ONE task of them (`chatMultiSelect`, ON)

## Definition of Done
- What must work: (1) **«حدّد» is an id of the ONE registry** (`message-menu-registry.ts`: `select`, Telegram's place right after «حوّل» / «حوّل للمحفوظة», offered only to the new screen — `surface: "v2"` — and only while `canSelect`; the old screen and the quick chat never receive it; never on a deleted message, a system line or to the owner reading silently). `MessageMenuV2` runs it itself (no door, no dialog) and no second list of items exists anywhere. (2) **The selection** is one tiny store (`src/lib/chat/selection.ts`) that the viewport attaches to (the company's switch + the open conversation), the menu of each message reads, and the pane header reads: a check on every message that can be picked (not deleted, not a system line, not pending), a press anywhere on the row toggles it, the menu / hover buttons / long press / double-click wait, unpicking the last message leaves, at most 100 (a 101st says so), a selection of another conversation is dropped. The header's content is replaced by the **bar**: the count in Arabic forms, «حوّل · انسخ · احذف · اعمل مهمة» in that order (a button that cannot apply is disabled, never missing; «حوّل» is not drawn inside the saved chat), a ✕; **Esc leaves** (taken in the capture phase before the shell's own Esc, which would leave the conversation — and not from a field, a dialog or a menu). (3) **`POST /api/chat/messages/forward`** `{ messageIds ≤ 100, targetIds ≤ 10, withoutAuthor? }`: each message is checked as forwarding one is (readable — 404 with the words of «not found» — then not a system line, not a poll, not deleted: 403) and ONE bad message refuses the WHOLE request before anything is written; then each target in turn with the single rule (`canPost`), ONE transaction per target writing every copy in the conversation's order, a target that refuses or fails is reported alone (`results: [{ targetId, ok, ids | error }]`, every refusal says `chat.e.post_denied` so the report is no oracle) and the others still get their copies; `withoutAuthor` writes the copies with no link to the original. (4) **`POST /api/chat/messages/delete`** `{ ids ≤ 100 }`: the single rule per id (`deleteLoaded`, the very code `deleteMessage` runs: own, or a moderator's, audited as before), a report per id; a message the person may not read and did not write is «not found», the same words as an id that does not exist; **a person who only reads through silent oversight deletes nothing and leaves no trace** (every id refused, no audit line); a deleted message is a tombstone for everybody and keeps its body for the archive. (5) **«اعمل مهمة» from a selection** = ONE task: `POST /api/chat/messages/[id]/task` takes `alsoMessageIds` — the source (`sourceMessageId`) is the EARLIEST message of all, the title is the first words of the first message that has any (`titleFrom`), the description quotes every message with author and time (the company's time zone, Western digits) then the link back to the first, cut to fit 4000 characters without ever cutting the link; **the visibility is decided over every source with the P0.3 policy** (`sourceOf` per message; ONE private source — a DM, a group, a restricted or a team's topic — makes the whole task «المعنيين بس» and «للمساحة كلها» needs the explicit choice AND `confirmPublic`, enforced by the server) — never by the first row. (6) **Caps and quota are the server's**: zod (100 / 10, none, a repeat counted once), the task's 100 in all, a quota of 20 forwards and 20 deletes a minute per person (a request refused before it writes costs nothing; `Retry-After` is the real wait). (7) **The switch `chatMultiSelect`**: ON by default, `dependsOn chatLayoutV2`; OFF = the three doors answer 404 `features.off` (the task door only when `alsoMessageIds` comes: one message still works) and the screen draws no «حدّد», check or bar.

## Switches
`chatMultiSelect` — ON by default. Off: `POST /api/chat/messages/forward` and `/delete` answer 404 `features.off`; `POST …/[id]/task` answers it when `alsoMessageIds` is sent; the screen draws no «حدّد», check or bar; nothing already made is touched. The screen learns the switch from the conversation's header when it carries `chatMultiSelect` (it does not yet, see below) and otherwise from ONE `GET /api/chat/messages/delete` (200 on, 404 off), kept five minutes; until it is known, or if asking fails, selection is OFF.

## Decisions used

P0.3: the batch task follows `sourceOf` per message. «اعمل مهمة» on a first message with no words (a voice note) keeps it as the source and takes the title from the first message that has words (a default title when none does).

## Independent review
There is no tool in this worker session to start a separate agent, so the review was the `code-review` skill (a forked, read-only reviewer that ran nothing) at the «high» level, over the diff and the new files. 10 findings, each judged here.
- **Real, fixed:** (1) the screen never honoured the company's switch because the header does not carry it — the probe door and `resolveMultiSelect` (OFF until known); (2) `deleteMessages` re-ran `findUnique` and `guard` per id — the messages are read once, the facts once per conversation, and `deleteLoaded` is the shared rule; (3) `messageToTask` loaded the person's facts and the conversation's for every message — `SourceFacts` reads them once; (4) the bar counted ids it could not act on — it counts, and acts on, what the window holds, and leaves when none is left; (5) «انسخ» had no day across days — it names the day when the selection spans more than one; (6) one shared quota bucket, charged before validation and a fixed `Retry-After` — two buckets, charged after the request is known good, the real wait; (7) the comment said «a second apart» for a millisecond step — corrected; (8) the delete report told an unreadable message from an unknown id — the same `not_found` now, with a test; (9) the PR file did not exist, and `canPost` was passed to `selectionActionsOf` and never read — both done.
- **Judged, kept:** the sequential writes of a big forward (see above): each transaction is bounded, and a client-generated id scheme is a bigger change than this package.
