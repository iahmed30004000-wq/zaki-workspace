# C1.4 + C1.5 — The client cache (one writer) and the start cache on the device

## Definition of Done
- What must work: (1) `src/lib/chat/cache/` is the ONLY code in the app that writes the chat keys `["chat","list"]`, `["chat","space",id]`, `["chat","conv",id,"header"]`, `["chat","conv",id,"messages"]` (an infinite query, windows of 50); a source-text guard fails on a `setQueryData` / `setQueriesData` on a chat key anywhere else. (2) The folder exports its WHOLE public surface from one barrel (`index.ts`): the writers `applySync`, `appendMessage`, `replaceMessage`, `tombstone`, `applyReads`, `upsertRows`, `removeConversation` (+ `markConversationRead`), `scheduleSync`, and the readers the C2 screen needs: `useChatList(folder)`, `useChatRow(id)`, `useChatHeader(id)`, `useChatMessages(id)`, `useChatSpace`, `useChatUnreadSummary`, with unread per row / per folder / per space derived from the cache. C1.6 (`pages.ts`) and C1.8 (`pending.ts`) only ADD a file and one export line. (3) `scheduleSync`: frames folded for 120 ms, ONE `GET /api/chat/sync?after=cursor` in flight, chained while the answer is full (`more`, or as many messages as the limit); reconnect, a focus after more than 60 s hidden, and coming online call it; a `reset` marks everything stale (what is on screen reloads) and the engine goes on from the cursor the answer carried; `removed` drops a conversation from every key. (4) The server's numbers win: a list refresh or a sync row replaces what the cache derived. (5) Prefetch: a mouse resting 150 ms on a row fetches header + first window; at startup the first window of the 3 most recent unread chats. (6) C1.5: the list, the header + last 50 messages of the 30 most recently opened conversations and the cursor are kept in IndexedDB `zaki-chat-<userId>` (20 MB cap, least recently opened evicted), hydrated at start so the list paints from the device, then the feed catches up; ONE function `wipeChatCache()` removes it all and is called at sign-out from BOTH client logout paths, on the sign-in page when nobody is signed in (the stream's `signed_out` takes the page there), when a DIFFERENT person signs in, and a guest / external partner never gets a copy.

Run and green besides them: `chat-outbox-ui`, `chat-outbox-queue`, `chat-outbox-send`, `chat-unread-badge`, `quick-chat`, `live-line-badges`, `lazy-shell`, `last-seen-dock`, `assistant-chat`, `realtime-kinds`, `shell-render`, `shell-bdi`, `shell-leading`, `arabic-ui`, `encoding-hygiene`, `no-hardcoded-colors`, `ui-font-floor`, `repo-hygiene`, `active-membership-guard`, `chat-oversight-guard`, `chat-arabic`, `theme-scrub`, `themes-decor-*`, `middleware-onboarding`, `owner-assistant-ui`, `task-visibility-guard`.
- Edge cases that matter: a burst of two new messages of one chat in one sync answer (it is NOT guessed into the window: a hole would be worse, the chat is caught up with `messages?after=`); a message deleted in the same answer; a window opened around an old message (it does not grow at the wrong end); my pending message replaced by the server's (by `clientId`, only between two copies of MY message); a patch that changes nothing writes nothing (it would make stale data look fresh), and a patch keeps the time the data was fetched (data from the device stays «stale» until the server confirms it); the cursor never goes back except in a `reset`; a cursor that arrives late (its request hung for 4 s) makes everything read before it stale again; a failed request retried after a growing pause, never on 401/403/404, never offline; a database another tab holds open (deleted as soon as it lets go); two tabs of one person (each write is ONE tab's whole snapshot with its own cursor, never a mix); a wipe in one tab (the others hear it on a `BroadcastChannel`, and a writer whose marker was taken away stops); a browser that refuses IndexedDB (works in memory, nothing stored, the wipe does not fail); a copy that is somebody else's / another format / damaged (never read, emptied); a tombstone with text in memory or in an old stored copy (stored and hydrated as a tombstone); identity or role unknown (nothing written, nothing wiped); localStorage refused or cleared (whose copy this is, is read from the `zaki-chat-*` databases themselves, so another person's copy is still found and wiped).

## The failing test, before the change
The guard `tests/chat-cache-writer.test.ts` was written first and run on a base with no `src/lib/chat/cache/`: 2 of its 6 tests failed (the folder and the barrel do not exist); the other 4 passed vacuously there (nothing writes a chat key yet), which is what a guard does before the thing it guards exists. Every other test file imports `@/lib/chat/cache/*`, which does not exist on `origin/main`, so each fails at import there (by reading, not a recorded run). What WAS recorded: two real bugs the new tests found in the first version of the code, fixed: (1) the persister committed an empty transaction on every flush when nothing had changed; (2) a row that moved up the list gave every row between its old and new place a new object (TanStack compares arrays by position), so every one of those row components would have re-rendered: the cache now shares structure BY ID (`share.ts`). **Three independent reviews** (read-only reviewers, they ran no test) found 9 + 10 + 7 problems, all real, all fixed, each with a test. The tests for the first two rounds' behaviour bugs were first run RED on the code as it was (7 red of 113; 8 red of 90 and 10 red of 155 on the later rounds). Examples: a deleted message that kept its card, forward and mentions; a deletion from the feed that left the quotes of it, the pinned bar and the row's line (also for a message no window holds, and for the forum row of its space); the 5-minute refresh that made unseen conversations stale so the device copy dropped them; a cursor that arrived late and was stored as current; another person's copy not found without the localStorage marker; a wipe that did not reach another tab, or reached it after the delete; a rewind of the cursor that an answer in the air undid; a boot that was still reading the copy when a wipe came and painted it afterwards; the stored cursor running ahead of an unfinished catch-up; a `reset` answer that left the old text on the device while no screen could write a new copy; a delete blocked by a frozen tab that left the copy readable; a damaged stored message that aborted the whole start; two tabs mixing records of different cursors; writes that could overlap; the eviction order forgotten at restart; two signed-out tabs wiping each other for ever.

## What changed
- **`src/lib/chat/cache/`** (new). `keys.ts` the four keys · `types.ts` · `reducers.ts` (pure: tombstone, merge a message into the windows, marks, rows, derived numbers) · `writer.ts` (THE writer: `applySync` and the rest, each one `patch()` that writes nothing when nothing changed and keeps the fetch time) · `share.ts` (structural sharing by id, the chat query defaults: stale after 5 minutes, kept 6 hours without a screen) · `unread.ts` (per row / folder / space) · `queries.ts`, `http.ts`, `constants.ts` (what each key fetches, 5 min stale, 1 h gc, no refetch on focus, no retry on 4xx) · `sync.ts` (`ChatSyncEngine`) · `runtime.ts` (one runtime per QueryClient: frames, online, hidden > 60 s, the 5-minute safety refresh, identity, hydrate, the persister) · `prefetch.ts` · `selectors.ts` (the hooks) · `persist.ts`, `opened.ts`, `device-store.ts`, `registry.ts`, `wipe.ts`, `identity.ts` (C1.5) · `driver.tsx` · `index.ts` (the barrel).
- **`src/app/providers.tsx`**: mounts `<ChatCacheDriver />` (renders nothing; on a device that never kept a chat it only asks `indexedDB.databases()` / the marker once and loads no cache code).
- **`src/components/shell/avatar-menu.tsx`**, **`src/components/onboarding-form.tsx`**: the two client logout paths call `await wipeChatCache()` (the avatar menu after `clearAllOutboxes()`, the onboarding page in its `finally`, so a failed request still wipes). It never throws and never waits long.

**How a sync answer is applied.** In order: `reset` marks every list, header and window stale (a window with older pages is first cut back to its newest page, so a refetch of it is one coherent window); `removed` drops conversations from every key (row, chips, forum view, header, messages); the messages go to their windows; the read / delivery marks follow (ticks of my private chats, the «who read» avatars, my own read on another device empties the row); the rows replace the derived numbers. **Where a message goes** is the one subtle point, because the server's `MessageDto` in the sync answer carries no conversation id (see «Not done»): a message already in a window is replaced in place (edit, reaction, deletion → tombstone); a NEW one is placed through the list row that names it as its newest message, but only when it is the only new message of its chat in the answer; with more than one (a burst, or one deleted at once) the chat is returned for a catch-up (`messages?after=<newest I know>`, in order, up to 6 steps). The day the server adds `conversationId` to those messages the cache reads it and none of this is needed.

**A fetch that was in the air while the feed moved on.** When a chat query settles and the engine applied events since it started, the answer was read BEFORE them and may have overwritten what they said; the engine goes back to where the request started and asks again (a replay is harmless, and a rewind survives an answer that is in the air at that moment).

**Cold start.** The cursor is learned BEFORE the list is read (`GET /api/chat/sync` with no `after` says where «now» is, one cheap request), so nothing that happens in between is lost; a replay is harmless. If that request takes more than 4 s the list is read without it, and when the cursor arrives everything read before it is marked stale again. A device with a copy continues from the STORED cursor instead.

**The device copy.** Every write replaces ALL records in one transaction (so what is stored is one tab's list + cursor + conversations, never a mix of two tabs'), a moment after the last change, only when something changed, only after the feed has answered once in this page, and only with data that is current (confirmed by the server in this page, or from the device and caught up from its cursor with no `reset` since). Each conversation record carries the time it was last opened, so «least recently opened evicted» survives a restart. Whose copy it is comes from the `zaki-chat-*` databases the browser lists (the marker in localStorage is a convenience that can be lost): any database that is not the signed-in person's is wiped before anything of theirs is read. A writer stops when its marker has been taken away (another tab wiped) and when another tab says so over a `BroadcastChannel` — which `wipeChatCache()` sends FIRST, before it deletes, and which a page that merely found nobody signed in does not send (two signed-out tabs would otherwise wipe each other for ever). A different person signing in wipes the DEVICE only (`broadcastWipe` + `deleteDeviceCaches`), not this page's memory, which already holds the new person's own data. Each runtime counts its wipes and resets: a boot that started before one does nothing more (it cannot paint a copy it read before the wipe). A database a frozen tab keeps open is EMPTIED before the delete is asked for, so nothing readable waits for that tab. A copy older than 30 days is not painted (and is emptied); a `reset` from the feed empties the copy at once (the next screen that refetches writes a new one); nothing is written while a conversation is being caught up (the stored cursor must not run ahead of a window that lacks messages).

**Unread.** Per row (its messages, or one when marked unread by hand), per folder (`all · unread · dm · spaces · mentions`, an archived row in none) and per space (a space's own row plus the private chats that carry its chip), muted rows countable or not. ⚠️ These are the LIST's numbers; the sidebar badge «الدردشة» (`/api/chat/unread`) is defined a little differently on the server (`pr/C1.2.md`: a topic never opened counts its whole history in the list, not in the badge). 🔧 The badge keeps asking the server and `useChatUnread` is unchanged; nothing derived is added to it.

## Owner actions
- ⚠️ **C1.5 PRIVACY — message text is now kept ON THE DEVICE** (IndexedDB `zaki-chat-<userId>`: the list, the header and the last 50 messages of the 30 most recently opened chats), in clear text, readable by anybody who can open that browser profile (the person at a shared computer, a browser extension, a device backup). 🔧 **Wipe**: `wipeChatCache()` deletes the databases of EVERY person the browser knows and the marker that names whose they were. It runs at sign-out (both client logout paths), on the sign-in page when nobody is signed in (so a session that ended without the button, a sign-out in another tab and the stream's «signed_out» all end there), when a DIFFERENT person signs in (before anything of the new person is read), and from «امسح ذاكرة المحادثات» (the button is C4.1, not built here). A guest / external partner's account never gets a copy, and one an older session left is removed. A deleted message is stored as a tombstone (no text, no files, no reactions); the owner-only extras (`history`, `original`, `notes`) are never stored. ⚠️ Not covered: a browser closed without signing out keeps the copy until the next page load finds nobody signed in or another person; the cookie session is what keeps it readable for the same person. 🔧 The honest limit is the operating system's own protection of the profile; the notice for the person is C4's («ذاكرة المحادثات»). Where the browser can neither list its databases nor keep the marker (an old browser in a private window) nothing can tell whose copy is there; such a browser also cannot keep it past the window.
- 🔧 **Needs a real browser and is NOT measured here:** open a cached chat and check that the list paints at once from the device (target under 100 ms: the number is the owner's to measure, it is not written as measured anywhere); DevTools → Application → IndexedDB shows `zaki-chat-<id>` after a minute of use, is gone right after «تسجيل الخروج» and after signing in as somebody else; one `/api/chat/sync` per burst of messages in Network (not one per frame); hover a row 150 ms: header + first window requested.

- **Late-committing events.** `pr/C1.2.md` asks `scheduleSync` to also resync on a frame whose id is not above its cursor; a handler of `useRealtime` / `subscribeRealtime` does not receive the frame id (`use-realtime.ts`, not in this package). The 5-minute safety refresh (everything on screen is asked for again, and the feed is asked) bounds the damage; exposing the id is a small change there.
- Header staleness is detected only where a sync row can say so (a topic renamed, closed, made private, archived, moved; a message's pin flag changed). A member count or a pin by someone else in a chat that has no other event waits for the next header fetch (5 minutes stale, the safety refresh, or opening the chat).
