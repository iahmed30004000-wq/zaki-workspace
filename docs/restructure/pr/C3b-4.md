# C3b.4 — Voice notes: speed, play next, mini player bar

## Definition of Done
- What must work: (1) **Speed 1× / 1.5× / 2×**, kept in `User.chatPrefs.voiceSpeed` (the field C3a.2 reserved: no schema, no migration, no new door). The pane reads it from `GET /api/me/chat-prefs` and saves a pick through the existing `PUT /api/me/chat-prefs` (a patch `{ voiceSpeed }`, through the chat cache's own `saveChatPrefs`, so the cache shows it at once). Default 1×. An old stored value without the field, or with a damaged one, reads as 1× and keeps the rest. (2) **Play next**: when a note ends, the next UNHEARD voice note of the conversation starts by itself: `nextUnheard(queue, currentSrc, heard)` in `src/lib/chat/voice-queue.ts` (pure) takes the first note AFTER the current one that was not played on this device and is not mine; nothing at the end of the queue. (3) **Mini player bar** under the pane header (`voice-mini-player.tsx`, mounted in `conversation-pane.tsx` before the pinned bar) while a note of this conversation plays (or is paused part of the way) and its bubble is out of sight (the list dropped it, or an `IntersectionObserver` says it is not on screen): the sender, the time left, play / pause, the speed, a stop, and a tap on the words goes to the message (the history's jump). (4) `voice-player.tsx` is ALSO the old screen's and the quick chat's player: an idle note at 1× draws exactly what it drew (play button, waveform, length, the hidden `<audio>`); the speed chip appears only on the note that is active, and on every note once a speed other than 1× was picked. `VoiceTranscript` («حوّل الصوت لنص») is not touched. No new switch.

## Not done here (recorded)
- A speed picked on the OLD screen or in the quick chat is kept for that page only: the save is wired by the pane (`VoiceMiniPlayer`), and those screens have no pane. The player there still works at the speed it has.
- «Heard» is per device and per session: the server keeps no «heard» mark for voice notes, and the plan adds no schema, so a reload plays notes again that were played before.
- The bar opens a prefs read (`GET /api/me/chat-prefs`) when a pane mounts; it shares the cache key (5 minutes) with the folders strip, so it is usually no extra request.
- No component test of the `IntersectionObserver` wiring and no real audio: this repository has no DOM test tool. The logic is in the pure functions and the engine, which are tested with a stand-in audio object.
- Not run here (shared `node_modules`): the full unit and database suites, `npm run build`. `docs/CODEMAP.md` is not regenerated (the integrator does).

## Independent review
There is no tool in this worker session to start a separate agent, so the review was the `code-review` skill (a forked reviewer that reads the diff and runs nothing). Eight findings, each judged here.
- **Real, fixed (the tests rewritten first):** (1) on iOS Safari a fresh audio object started from an `ended` event with no tap is refused, which would have broken the walk silently: the engine now owns ONE audio object, unlocked by the first tap, and plays every note through it (the bubble's `<audio>` only reads the length); (2) the bar hid itself when the playing note's message was no longer in the loaded window: the snapshot keeps the note from the moment it started; (3) two notifications between two notes (an idle moment, the bar and the chips flickering): the walk starts the next note directly; (4) the same note drawn twice overwrote its own registration: bubbles are counted per address; (5) a failed element creation left the state inconsistent: with one object created lazily, no audio means nothing happens; (6) `getSnapshot` closure rebuilt each render: `useCallback`.
- **Answered without a change:** the speed save is not wired on the old screen (recorded above); with no `IntersectionObserver` a mounted bubble counts as on screen (every supported browser has it).
