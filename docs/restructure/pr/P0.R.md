# P0.R — What the independent review of phase P0 found

An independent reviewer (a fresh session that had only the code and the Definition-of-Done files) read the six P0 steps and
found real holes. Five were reproduced by a test that failed first; two more are closed by a source-level guard; the rest are
listed below as not fixed, with the step that owns them.

## Definition of Done
- What must work: (1) a task made from a private conversation is published («المساحة كلها») only after a confirmation, on the
  task page too (422 `work.confirm_public_required` without `confirmPublic`; the page asks once and sends again); (2) the
  reporting line is per company: a person who manages somebody in company A manages nobody in company B; (3) «التبعيات» does
  not name a private task the person may not open; (4) the time report leaves out private tasks' entries for a person who
  is not one of the task's people, a manager of the space or an oversight holder; (5) project, board, milestone, department
  and Today counts do not count private tasks the person may not open; (6) a key file without BOTH passwords stops the Android
  workflow instead of publishing a debug-signed APK over the real one; (7) the secret scan also reads the call form
  `storePassword("…")` and a setter.
- Tests: `tests/db/p0-review-fixes.test.ts` (new, 6 cases for 1–5), `tests/scan-secrets.test.ts` (extended, 2 more forms),
  `tests/android-app.test.ts` (extended, the workflow guard). Must stay green: `tests/db/task-visibility.test.ts`,
  `tests/db/privacy-matrix.test.ts`, the whole suite.
- Edge cases that matter: the line per company is carried by `WorkScope.reportIds` (a map by company) and `spaceOrg`; the
  raw-SQL form of the rule joins one clause per company (an empty set of clauses is `Prisma.empty`); a task NOT made from a
  private chat still goes public with no confirmation; the oversight holder and the creator still read everything they did.
- Blockers: CI red · an old test red · a secret exposed · a destructive migration (none).

## What changed
- `src/server/chat/private-source.ts` (`sourceIsPrivate`); `tasks.ts` `updateTask` refuses `SPACE` on a task made from a private
  source without `confirmPublic`; the route accepts the field; `task-detail.tsx` asks once and sends again.
- `reporting-line.ts` takes the company; `team-scope.ts`: `WorkScope.reportIds` is a map by company, new `spaceOrg`,
  `reportsOfSpace`; `taskParticipantWhere`, `canSeeTaskParticipants`, `taskVisibleSql` and `mayChangeVisibility` use it.
- `task-links.ts` filters the other end of a link by the rule; the route passes the viewer.
- `time-tracking.ts`: the report's where adds the participants rule (an entry with no task stays).
- Counts: `api/projects`, `projects/page`, `projects/[id]/page` (board and project counts), `departments.ts`, `today.ts`,
  `milestones.ts` (an optional viewer; the page and the route pass it).
- `android.yml`: the key step fails when the key file is set and a password is not; `scan-secrets.mjs`: the Gradle rule reads
  `storePassword("x")` and `setKeyPassword("x")`.

## Not fixed here (recorded, with the step that owns it)
- The owner board and the person page select task TITLES of done and open tasks (`owner-board.ts`, marker «owner-level
  aggregate»), and `policy/board.ts` also serves mode `team` (a holder of `board.team`, teams by `Team.leadId`). So a team lead
  who is not in the reporting line can read the titles of a team member's private tasks there. The plan narrows that
  audience in A1.3; until then the marker is not the whole truth. ⚠️ 🔧 Do not turn `board.team` on for anybody before A1.3.
- Existence leaks of one bit: the chat chip trusts `canModerateHere` of the conversation's space, not the task's; goal links
  (`okr.ts`) count task ids without the rule; deleting a board column answers «not empty» for a column of hidden tasks. None
  opens the task (404). Listed for A1.
- `taskVisibleSql` has no production caller yet; every raw-SQL reader carries a marker, and some markers are loose
  (`rewards.ts:294` says «passed requireTaskAccess» but is an owner-only total). The guard test cannot see nested relation
  selects and `_count`; extend it when the readers are next touched.
- The migration's index is not `CONCURRENTLY`; it briefly blocks writes on a large Task table at deploy. Acceptable at this size.
- Chat treats a partner without `archive.view` as a space ADMIN of every space (reads all «مقطع» topics); tasks do not. The
  owner's decision D-P4 covers it; it is on the A1 list.
