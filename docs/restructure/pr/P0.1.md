# P0.1 — Silent oversight follows the capability `archive.view`, not the OWNER rank

## Definition of Done
- What must work: an OWNER-rank person (a partner) whose `archive.view` was taken away no longer reads other people's
  DMs or restricted topics he is not in: those answer 404, are absent from the chat home, the search and the counts, and
  cannot be posted in. He is a normal participant: he reads and writes the OPEN topics of every space like a space
  manager, and his reading leaves a normal read mark. The primary owner (and a partner who still holds the capability)
  reads everything silently exactly as before. A partner's sheet has a switch «الأرشيف والرقابة», shown only to the
  primary owner. Changing a rank or a permission is announced on the live line so a connected partner loses the
  conversation at once.
- Tests: `tests/db/chat-partner-oversight.test.ts` (new), `tests/chat-oversight-guard.test.ts` (new, source text),
  `tests/members-ui-oversight.test.ts` (new). Must stay green: `tests/db/partners.test.ts`,
  `chat-owner-reads-dms`, `archive-capability`, `topic-privacy`, `chat-admin-scope`, `chat-org-isolation`,
  `chat-topics-not-dms`, `realtime-replay-gate`, `tests/chat-logic.test.ts`, `tests/chat-message-menu.test.ts`, the
  members-ui tests, `tests/codemap.test.ts`.
- Edge cases that matter: a hand-made `OrgFacts` without the new field is read as "an OWNER holds oversight" (the unit
  tests build such facts); `loadOrgFacts` always sets it. A partner without oversight is a space ADMIN of every space
  (no `WorkspaceMember` row needed), as `requireWorkspace` already treats the OWNER rank. Purging («حذف نهائي»),
  muting, creating topics and the owner's own assistant stay decided by rank (management, not reading) — each such line
  carries `// oversight-ok: <reason>`.
- Blockers: CI red · an old test red · a secret exposed · a destructive migration (none: no migration) · a feature
  removed instead of marked (none).

## What changed
- `src/server/policy/conversation.ts`: `OrgFacts.oversight`, `hasOversight(org)` (ONE definition: the OWNER rank AND
  `effectiveCapabilities(...).has("archive.view")`, the same rule as `holdsArchiveView`); `canRead`, `canPost` and
  `canModerate` use it; an OWNER-rank person without it is a space ADMIN of every space.
- Chat services: `messages.ts` (reactions, pins and read marks are silent only for oversight; the viewer carries
  `oversight`), `redact.ts` and `poll-shared.ts` (history, originals of deleted messages and the silent poll viewer),
  `topics.ts` (the `me` flags; read marks of an OWNER-rank person who lost the capability show like anybody's),
  `home.ts` (`canOversee`, which restricted topics are listed, `silentOversight`), `services/watch.ts` and
  `policy/call.ts` (a call or a session in a private topic is not joined by rank).
- `src/server/services/accounts.ts`: a change of rank or of permissions emits `membership.changed`, so the hub forgets
  the visibility cache of that company at once.
- `src/lib/members-ui.ts` + `ar.members.json`: the switch «الأرشيف والرقابة» on a partner's sheet, for the primary
  owner only, with ⚠️ and 🔧 in its hint.
- `AGENTS.md` «Access model»: one primary owner plus partners; silent oversight is the capability, never the rank.
- `docs/CODEMAP.md` regenerated (`node scripts/codemap.mjs`), as its test requires.

## Noticed
- Different from the plan: `OrgFacts.oversight` is optional instead of required, with "an OWNER holds it" as the reading
  of an absent value — so the unit tests that build `OrgFacts` by hand (`tests/chat-logic.test.ts`,
  `tests/chat-message-menu.test.ts`) keep their meaning; production always sets it in `loadOrgFacts`.
- Different from the plan: `unread.ts` keeps its rank condition (marked `oversight-ok`): the rank is a space ADMIN of
  every space, and the counts only ever use conversations with the person's OWN row, so silence is unaffected.
- A post to a restricted topic the person may not read answers 403 (not 404) — as it did for any person before this
  step; hiding the existence there too is a separate change.
