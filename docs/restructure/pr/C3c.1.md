# C3c.1 — The checklist in chat: «قائمة مهام» (`chatChecklists`, OFF by default; needs `chatLayoutV2` to be seen)

## Definition of Done
- What must work:
  1. **Schema (two NEW tables, additive).** `ChatChecklist` (`messageId` unique → `ChatMessage` cascade, `othersCanAdd` default false, `othersCanTick` default true) and `ChatChecklistItem` (`text` VARCHAR(200), `position`, `addedById`, `doneById?`, `doneAt?`, index `(checklistId, position)`), one migration `20261126130000_chat_checklists`. `ChatMessage.kind` gains the TEXT value `CHECKLIST` (a text column: no enum change); the body is the TITLE. `RELEASED.txt` untouched, `lint-migrations` clean, `prisma migrate diff --from-migrations … --to-schema-datamodel …` says «No difference detected».
  2. **Send.** The message POST accepts `checklist: { items: string[1..30], othersCanAdd?, othersCanTick? }` (the title is `body`, at most 200 characters; an item at most 200 characters, blanks dropped, spaces folded). Never with files, a voice note or a poll; never for a GUEST; a retry with the same `clientId` is the same list. Any conversation where a non-guest may post (a topic, a group, a private chat). The company's switch closes it (404 `features.off`).
  3. **Doors.** `POST …/messages/[id]/checklist/items` (add: the author, or anybody who may post when `othersCanAdd`), `PUT …/items/[itemId]` `{ done }` (tick and untick: the author, or anybody who may post while `othersCanTick`; ticking again keeps who ticked first and when), `PATCH …/items/[itemId]` `{ text }` and `DELETE …/items/[itemId]` (the item's author, the list's author, a moderator). Every door: zod, `withApi`, the policy of the conversation, the limiter (120 changes a minute), a row lock on the list (the 30-item limit holds under a race), the switch. Every answer is the message as the caller now sees it.
  4. **Oversight and guests.** The owner reading in silent oversight (not a row of the conversation) ticks, adds, rewords and removes nothing (403 `chat.e.join_first`: no trace, like a poll; after he joins he is one of the people). A guest reads the list and the ticks, never who ticked, and writes nothing. Nobody writes to a deleted message or a closed topic.
  5. **Live line.** New realtime kind `checklist.changed` in the ONE list `REALTIME_KINDS` (ids only: conversation, message, space; never who ticked or what an item says); the sync feed returns the presented message (`MESSAGE_EVENTS`).
  6. **Bubble.** The title (bold), a box per item, «خلّصها فلان · 10:20» under a done item (a guest reads «خلصت · 10:20»), the progress «3 من 5», «+ أضف بند» where the server says `canAdd`, a pencil and a bin on the items `canEdit`, and «اعمل منها مهمة». The list's row preview says «☑️ العنوان (3/5)» where the row carries the count and «☑️ العنوان» without it.
  7. **«اعمل منها مهمة».** The bubble's button runs the one door that makes work of a message (`MakeWorkDialog` → `messageToTask`: the project's rules, `sourceMessageId`, privacy by P0.3 — a list from a private conversation makes a PRIVATE task and a public one needs `confirmPublic`) and then the dialog itself asks `POST …/checklist/steps { taskId }` (so the bubble's button AND the message menu's «اعمل منها مهمة» both write the steps: the dialog sees the message's kind): one `TaskStep` per item through the steps service (`insertStep`), done items done by whoever ticked them, only for the task whose source IS this message, only while it has no step, only by a person who may write that task's steps (the task's own guard: a private task is not even found by a person it does not concern; a guest and a silent reader write none; the `taskSteps` switch closes it).
  8. **Attach menu.** «قائمة مهام» on the paperclip (only with `me.canChecklist`) opens a dialog like `PollDialog` (a title, 1 to 30 items, Enter opens the next item, two choices: others add, others tick). It is run by the menu itself (see «Not wired» for why).
  9. **Nothing else reads an item.** The bell, the push, the search, the chat list, the assistant, the semantic index, the ticket rules and the digest see the TITLE only (the items are in their own table and only `presentChecklist` turns them into words, for a person who reads the conversation); a checklist is not forwarded (a copy would carry no items). The old screen draws a CHECKLIST as its title text.
  10. **Switch** `chatChecklists` (OFF by default; group chat, depends on `chatLayoutV2`). OFF: the routes answer 404, a checklist cannot be sent, the menu entry is not drawn, a list already made is shown with no box or button that works (the data stays and comes back).

## Why a poll's table and a task step cannot hold it (README rule R9)
- `PollVote` is one CHOICE per person among fixed options (`@@unique [pollId, optionId, userId]`); a checklist item has ONE shared done-state for everybody and people ADD items after the list was sent. Forcing it into `Poll` would make every item an option and every tick a vote of one person that the others overwrite.
- `TaskStep` hangs on a `Task`, and a task needs a project, a board and a column (and an assignee rule, a privacy value, a notification): the heavy path a quick list in a chat must avoid. A list in a private conversation would also have to invent a private task for nothing. When the list WANTS to be work, «اعمل منها مهمة» uses the real `TaskStep` through the existing service, and nothing is copied twice.

## Independent review
A read-only review of the working tree (`/code-review`, medium; it ran no test) found nine things. Taken and fixed, the first four with a failing test first (the two unit tests were run red, the database ones were written with the fix in the same sitting and are green):
1. **Rewording and removing ignored `canPost`**: in a closed topic, for a muted person or in a poster-only topic the author could still reword or delete an item (and the pencil was drawn), while add and tick were refused. Now `mayEditItem` and the door need `canPost` (a moderator too: a closed topic is frozen).
2. **«اعمل منها مهمة» was not atomic**: two presses at once could both see no step and insert twice; a failure half way left half a list. Now the steps are written under the list's row lock (the second press waits, then finds them: 403), a failure takes back what was written, and the items are read under the lock.
3. **Any reader of the message who works in the space could copy the items into a task he did not make**: the steps door now needs the task's CREATOR to be the caller (and the source to be this message).
4. **Editing the title** skipped the title rule of the send (empty, longer than 200 characters): the same rule holds for an edit now (`chat.e.checklist_title`).
5. **An item of invisible characters** (a zero width space, the direction marks) passed as words: such an item is a blank one now, on the server and in the dialog (the Arabic joiner inside a word stays).
6. **The bubble's guard** was a stale closure (two presses in one render tick made two requests, and the answers could arrive in the wrong order): it is a ref now.
Not taken: the limiter's `check` then `hit` and its counting of refused calls (the same as the poll's limiter, a shared helper's behaviour); `Promise.all` inside the add transaction (harmless; the row lock is what makes it correct); `canMakeTask` read from the cached header (the server decides again; with no header the button is simply not drawn, and the menu's own item stays); a stale open editor after a remote removal (the save answers 404 and says so).
