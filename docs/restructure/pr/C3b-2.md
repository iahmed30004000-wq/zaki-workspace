# C3b.2 — Link previews (`linkPreviews`, ON)

## Definition of Done
- What must work: (1) **After a message with a link is sent, the server reads that page and the bubble can show a card** (title, description, site name, one picture). The fetch is an after-send step of C1.8 (`runAfterSend`, the LAST step: the bell and the ticket rules never wait for another company's web server): it never delays or fails the send, an expected refusal is logged by reason (`chat.link_preview_failed`, never the address), anything unexpected is thrown into `chat.after_send_failed` with the step name `link_preview`. A message already stored is NEVER fetched on read; only the first link of a plain TEXT message, only https, never a link to this app's own address. (2) **Only through `net-guard`**: `assertPublicHttpsUrl` on the first address AND on every redirect hop (redirects are followed by hand, at most 3; a public page that redirects to 10.x, 169.254.169.254 or an `http:` address is refused before that address is asked for), 3 seconds for the whole request, 512 KB of HTML (the rest is not read), HTML only. No cookie, no authorization header, no referrer. (3) **The picture** is downloaded through the same guard (at most 1 MB, judged by its bytes: png, jpeg, gif, webp, never an svg), stored with `ingest` and served ONLY by `GET /api/chat/messages/[id]/preview/image` after the message's reading rule (404 for everybody else, a deleted message included); never the site's address, never a Drive link. (4) **`message.enriched`** is in `REALTIME_KINDS` (ids only) and `syncFeed` returns the presented message with its card. (5) **Per viewer** through `presentMessage`: no card on a deleted message (the owner's original neither), none for a failed page, a guest sees it as the text, the company's switch off hides it. (6) **The sender is in control**: `noPreview` on the send (the composer's ✕ before sending) and «شيل المعاينة» (`DELETE /api/chat/messages/[id]/preview`, the AUTHOR only: 403 for a reader who is not, 404 for a stranger). (7) The **guide** says it (⚠️ + 🔧) and the **switch** `linkPreviews` is ON: off = no fetch, no card from send, sync, the messages window or a poll, the routes 404, the data stays. It works only where the new chat screen (`chatLayoutV2`) is on too (`linkPreviewsOn`), because that screen draws the card and holds the ✕ and «شيل المعاينة». (8) **Wired in this merge (review fixes)**: the messages window and polls ask the switch; the composer's ✕ travels with the send; the bubble draws the card; «شيل المعاينة» calls its door; a card arriving after the send reaches the open screen through the sync feed.
- The tests: `tests/link-preview-wiring.test.ts` (the ✕ in the payload, the optimistic send and the outbox, the card in the bubble, the removal door and its toasts, the cache merge), `tests/link-preview-parse.test.ts` (the tokenizer reuse, the tag parser, the guarded request with a stub network, the picture rules, the presenter, the card, the composer line, the menu id, the guide), `tests/db/link-previews.test.ts` (17 cases against a real database, stub network), a privacy-matrix block (`tests/db/privacy-matrix.test.ts`, one row per kind of conversation × nine kinds of person) and the switch in `tests/features.test.ts`.
- The edge cases that matter: a private literal address, a name resolving to a private address (any one of its answers), a redirect to the cloud metadata address, an `http:` redirect, a fourth redirect, a page that is JSON, a page over 512 KB, a picture over 1 MB (declared or not), an svg sent as `image/png`, a picture whose address is private, a site that is down (not asked again for 10 minutes), the same page in two messages (read once) and in two companies (two rows, two pictures), an edit that changes the first link (the card goes, the new link is not visited), a message deleted or removed while the page is being read.
- Blockers: none known for this package.

## What changed
- **Schema (additive, `prisma/migrations/20261123101400_link_preview`)**: a NEW table `LinkPreview` (`id`, `orgId`, `urlHash` unique, `url`, `title?`, `description?`, `siteName?`, `imageFileId?`, `status` OK|FAILED, `fetchedAt`) and `ChatMessage.previewId String?` (+ index, FK `SET NULL`). `migrate diff` against the migrations is empty; the migration linter is clean. **Why no existing table holds it**: `StoredFile` is a file WE keep (its row is the picture, and is used for it), `Card`/`Idea` are our own content, `ChatMessage` is what a person wrote and must not be rewritten with a page's words; nothing stores metadata fetched from somebody else's page, and one page linked in many messages must be read once. Two additions beyond the spec's column list, both on purpose: `orgId` (cascade on company deletion, and a tenant), and `urlHash = sha256(orgId + address)`, so the unique key carries the tenant (AGENTS: «idempotency keys always include the tenant») and one company's card and picture never serve another's.
- **`src/server/chat/link-preview.ts`** (new): `previewUrlOf` (the FIRST link by `firstLink` of C3b.1's tokenizer: no second address pattern; https only; not this app's own host), `parseOpenGraph` (og tags with twitter and `<title>`/description fallbacks, entities decoded once, tags stripped, invisible and direction characters dropped, lengths capped, comments/scripts/styles ignored, a `>` inside a quoted value handled), `guardedGet` / `fetchLinkPreview`, `linkPreviewAfterSend`, `detachPreview`. A page read within 7 days is reused by the company; a failed page is left alone for 10 minutes; at most 6 pages are read at once by a process (the rest are skipped and logged). ## Decisions to know
- **The picture's purpose.** It is stored with `ingest` as `CHAT` (as planned) and then TAGGED `LINKPREVIEW`, because `purgeOrphanUploads` deletes every `CHAT` file that no message attaches after 24 hours: the card would lose its picture the next day. The alternative (keep `CHAT` and add `linkPreviewImages: { none: {} }` to that purge's query in `attachments.ts`, a file of another package) is a one-line change; say which you prefer. `assertMayReadFile` treats the tag like any chat file: only the uploader reads it by id through the files door, everybody else only through the preview route.
- **A card is not made for an edit or a forward.** Telegram re-previews; here a new link on edit is not visited (the plan says «fetch after the send commits») and a forwarded copy has no card.
- **No preview text goes to a model.** The cards are never given to `buildChatPrompt`, the translator or the digest, so there is nothing to strip there; if a later step adds them, the page's words must go through `stripFormatting` first (C3b.1).
- ⚠️ Known limit, inherited from `net-guard`: the name is resolved by the guard and again by `fetch` (DNS rebinding). 🔧 Closing it needs a connection-level hook (an undici dispatcher that pins the address), a separate step.

## Switches
`linkPreviews` (ON by default, `src/lib/features.ts`, name and hint in `ar.features.json`, pinned in `tests/features.test.ts`). It acts only where `chatLayoutV2` is ON too (merged OFF today, so nothing is visited until the owner turns the new chat screen on). OFF: no page is visited, send, sync, the messages window and polls carry no card, the picture and removal routes answer 404, the cards already made stay in the data and come back with the switch.

## Owner actions
To see link cards the owner turns on «شاشة الدردشة الجديدة» (`chatLayoutV2`, off as merged). If the owner does not want the server to visit links, he switches «معاينة الروابط بالدردشة» off in «الإعدادات» ← «الميزات».

## Not done here
- The OLD chat screen and the quick chat (`ChatComposer`, `MessageItem`) have no card, no ✕ and no «شيل المعاينة»: that is why `linkPreviewsOn` needs `chatLayoutV2`. Making them show cards is not planned.
- Not built: re-preview on edit, a card on a forward, a retention job for old `LinkPreview` rows and their pictures (they live as long as the company), a per-company rate limit on page reads beyond the send limiter and the in-flight cap.
- The composer hook itself has no render test (the repo has no hook renderer): its wiring is pinned by reading the source (`link-preview-wiring.test.ts`) and every layer below it is tested for behaviour; the database test posts the exact payload the screen builds through the messages door.
- A header cached before this deploy has no `linkPreviews` field: the bubble draws no card until the header is fetched again, but the composer STILL draws the warning line and the ✕ (it is hidden only when the header says the switch is off), so the person is never visited without being told.
- The ✕ is one flag for the box's link: a paste dialog's caption sent while the flag is set carries `noPreview` too (the safe direction: no visit rather than a surprise visit).
