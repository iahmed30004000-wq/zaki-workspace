# Q1.4 — An order's state: chips and «/طلب»

## Definition of Done
- What must work: (1) the orders system's own order-number shape copied as a constant with its source named (`src/lib/oms/order-ref.ts`), plus ONE
  addition of ours — the first part must hold a letter, so a phone number written «079-1234-5678» is never a chip; (2) the NEW table `OmsOrderState`
  (a small cache: order number unique per company, the internal id, the states, product name, quantity, when it moved, when we asked) — no existing
  table holds another system's order state; (3) the lookup `GET /api/orders/state?number=&conversationId=`: staff only, the person must be able to read
  that conversation (else 404 and the orders system is not asked), kept 60 seconds fresh, a failed refresh shows the last known state marked old,
  only the fields of the contract are ever stored; (4) an order number written in a plain message becomes a chip (a button; nothing is asked until it is
  pressed); (5) «/طلب <رقم>» sends a CARD message holding `{ type: "order", number }` and the line «طلب <number>» — no state, no customer data — and each
  reader's screen asks for the state; (6) states are said through an Arabic map, an unknown word is «حالة غير معروفة», never the raw word; (7) the
  switch `orderStatus`, OFF, needs `omsLink` (linked and connected).
- Tests: `tests/order-ref.test.ts` (8), `tests/db/order-state.test.ts` (13), `tests/recall-client.test.ts` (7); must stay green: the chat tests, the
  Q1.3 tests, the whole suite.
- Edge cases that matter: a phone number is never a number; an answer for ANOTHER order is no answer; the old orders system (no by-number door) is
  told as «حالة الطلب بتتفعّل بعد تحديث نظام الطلبات»; a number glued to other letters is not found inside them.
- Blockers: CI red · an old test red · a secret exposed · a destructive migration (none).
