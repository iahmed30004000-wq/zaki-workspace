# S5.2 — ONE Telegram-like forward sheet (switch `chatMultiSelect`, ON; no new switch, no schema)

## Definition of Done
- What must work: (1) **ONE sheet for both flows.** The single «حوّل» of a message and «حدّد» then «حوّل» open the same sheet (`src/components/chat/v2/forward/forward-sheet.tsx`): a search box (Arabic-aware: vowel marks, alef / ya / ta marbuta and Arabic-Indic digits are ignored), «الرسائل المحفوظة» on top, the recent conversations as a strip of pictures, then every place the person may write in **in every space they are in** (one group per space, with its name) and their private chats and groups, each with a picture; up to **10** picked; an optional **comment**; «بدون اسم المرسل الأصلي»; ONE «إرسال»; a toast «تحوّلت إلى …» with **«افتح»** (only when exactly one target was asked and it worked) that jumps to that conversation. A bottom sheet on a phone, a side panel on a computer. (2) **A new picker door** `GET /api/chat/forward-targets` (`src/server/chat/forward-targets.ts`) lists, for the sheet, the topics of EVERY space the person is in plus their private chats, the saved chat on its own (`saved: { id | null }`: made on first use through the dm door) and the recents. `/api/chat/home` is NOT widened (it stays the current space's). (3) **It is a hint, never a permission.** The topics are judged by the chat list's own two rules, now exported from `home.ts` (`topicListed`, `topicPostable`; `chatHome` uses the same functions), plus: never an archived or closed topic, never a private chat whose other person is no longer ACTIVE, never a guest's private chat or saved chat. Every target is decided AGAIN on send (`guard` + `canPost` + an archived topic is refused too), the whole request is still refused atomically when one message cannot be forwarded, and every refused target says the same words (`chat.e.post_denied`). (4) **The comment** (`comment`, ≤ 1000 characters, optional) is written in the SAME transaction as one more message AFTER the copies in each target (a millisecond later than the last, so it can never sort before one); a target that refuses gets neither copies nor comment. (5) **The receiver is NOTIFIED**: `notifyAfterSend` (the path `sendMessage` takes) is now exported and called after each target's commit (one notification per target, never per copy): the private chat's other person gets the bell and the push under their own mute and choices; what a topic tells whom stays the send's rule (today: mentions and replies only); the forwarder is never told of their own forward; the saved chat tells nobody. The words: the comment, else the one message's words, else «حوّل لك N رسائل». A failure there is logged and never fails the forward. Both doors notify (the single `POST /api/chat/messages/[id]/forward` too). (6) **The ORIGINAL author is kept**: a forward of a forward points `forwardedFromId` at the original (`msg.forwardedFromId ?? msg.id`), so the header «محوّلة من» names the first author, not the person who passed it on; «بدون اسم المرسل» leaves no link at all, also on a re-forward. (7) **The header is tappable**: a button; the tap asks `GET /api/chat/messages/[id]/forward`, which answers `{ conversationId, messageId }` ONLY when the viewer may read both the copy and the original and the original is not deleted (else the same 404 for every case; a guest always gets 404 and never even gets the header: the `redact.ts` rule is pinned by a test); the same conversation jumps, another one opens by its address (`?m=`). (8) **`ui/toast.tsx`** takes an OPTIONAL third argument `action: { label, onClick }` (P2.1 depends on it); the old two-argument calls are untouched. (9) **Switch:** the picker door and the multi door are behind `chatMultiSelect` (404 off). With it off the single «حوّل» is the old one-tap list (`ForwardDialog`, unchanged) and the old chat screen is not touched.

## Independent review
No tool to start a separate agent was available, so the review was the `code-review` skill at the «high» level (a read-only reviewer that ran nothing). Its first run picked the wrong worktree (it reviewed another package) and was discarded; the second, pointed at this worktree, gave 9 findings, each judged here.
- **Real, fixed:** (1) the saved chat was offered inside the saved chat itself (not filtered by `from`) — `savedRowFor`, with a test; (2) a partial answer closed the sheet and ended the selection, so a retry meant rebuilding everything and copying twice into the targets that worked — now the sheet stays open on the picks that failed (`remainingPicks`) and the messages stay selected; (3) the author's name was read once per target — once per forward (`authorNameOnce`); (4) a toast with a button disappeared after 4 s — 8 s when it carries an action (`TOAST_ACTION_DISMISS_MS`); (5) the person's own chat with the assistant (a restricted topic whose title is the assistant's) was offered — it is left out of the picker, with a test; (6) the private import of Next's router context (`next/dist/...`) — replaced by the public `useRouter()` caught when there is no router.
- **Judged, kept (recorded):** the comment is a plain text row, so it does not run the send's after-work (auto-ticket rules, link preview, search vector, the assistant's answer): a forward's comment is a note, not a command, and running the company's rules over it was not asked for; a forward has no idempotency key, so a lost response followed by a second press can copy twice (the old forward had the same limit; a client id per forward is a wider change); the picker sends the whole list of the person's places on each opening (no pagination: the list is the person's own places, the same order of size as the chat list); `selection-bar.tsx`'s old sender is dead code (not on this package's paths, see above); one `conversation.findUnique` per target for `archivedAt` (one cheap indexed read per target, bounded by 10).
